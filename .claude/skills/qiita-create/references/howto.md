# 手順型の記事の書き方

## いつ読むか

手順型の記事（導入・移行・構築の手順を、読者が同じ結果を再現できる形で残す記事）を書くときに読む。概念解説型は `concept.md`、ハマりどころ型は `troubleshooting.md`、体験記型は `experience.md` を読む。

読むタイミングは記事タイプを手順型と判定した直後、構成を決める前。この型の成否は一つの基準で決まる。**読者が上から順に実行して同じ結果に到達できるか**である。理解の深さや網羅性は、その次に来る。

## 必要な入力

共通の核（`planning.md`）に加えて、次を確定する。

- **到達状態**: 手順を最後まで実行すると何ができるようになるか。スクリーンショット・GIF・最終的な設定ファイルのどれで見せるかも決める
- **前提条件と環境**: 必要なランタイム、事前に入っているべきツール、それぞれのバージョン
- **手順**: 実行順に並べ直したコマンドと設定。書き手が試行錯誤した順ではなく、再現に必要な順
- **成功を確認する方法**: 各段階が正しく完了したことを読者がどう判定するか
- **失敗時の戻し方**: 既存の環境やファイルを置き換える手順について、元に戻す方法

自分の環境で通しで再現していない手順は書かない。再現していない箇所があるなら、その箇所を未検証と明記する。

## 記事の骨格

| 位置 | 置くもの |
| --- | --- |
| 冒頭 | 何が達成できるか・前提環境 |
| 駆動軸 | 手順の段階 |
| 末尾 | つまずきやすい点・運用上の注意 |

駆動軸は手順の段階であって、書き手が作業した順ではない。試行錯誤して行きつ戻りつした過程は、体験記型なら価値になるが、手順型では読者を迷わせるだけである。手順として整理し直して並べ、経緯は「なぜこの構成にしたか」の節へまとめる。

段階の切り方は 2 通りある。工程で切る（インストール → 初期化 → 設定 → ビルド）か、対象で切る（ツール A の導入と設定 → ツール B の導入と設定 → 連携）か。複数のツールを組み合わせる記事では後者にし、各ツールの節を「インストール」「設定」で揃えると、読者が自分の詰まった箇所へ戻りやすい。

## 固有の書き方

### 冒頭の書き方

- **完成状態を先に見せる**: 動作している画面のスクリーンショット、操作の GIF、最終的な設定ファイル全体のいずれかを冒頭に置く。手順を最後まで実行しないと何が手に入るか分からない記事は、読者が着手を判断できない。動きのあるツールなら、静止画より GIF のほうが伝わる
- **画像を置いたら読みどころを一文添える**: 「ホストでは実行できなかったコマンドが、コンテナに入ったことで実行できるようになった」のように、その画像のどこを見るべきかを書く。画像だけを置くと、読者は何が変わったのかを自分で探すことになる
- **前提環境を独立した節にする**: 必要なランタイム、事前にインストール済みであるべきツール、エディタや拡張機能を箇条書きにする。本文中に散らすと、読者は手順を進めながら不足に気づくことになる
- **完成物へのリンクを置く**: 動くサンプルリポジトリや最終的な設定一式を公開しているなら、冒頭近くにリンクする。手順を追う前に全体を見たい読者と、詰まってから答え合わせをしたい読者の両方に効く

### 手順の書き方

- **上から順に実行できる形にする**: コマンドは実行順に並べ、途中に読み物を挟まない。関連するコマンドを 1 つのコードブロックにまとめ、行コメントで各行の意図を書くと、読者はブロックごとコピーして流せる。「この設定を先にしておく必要があります」のような後出しの前提を作らない
- **バージョンを固定して書く**: インストールコマンドにバージョンを明示する。バージョンを書かない記事は、書いた時点では動いても、読まれる時点で動く保証がない。特に、特定のバージョンでないと動かないことが分かっている依存は、その旨とバージョンを必ず書く
- **各手順が何のために必要かを一文添える**: コマンドが生成するファイルやディレクトリの役割、そのツールが担当する範囲を短く書く。これがないと、読者は丸写しで動かせるが、後から自分の環境に合わせて変えられない。ツールを複数組み合わせる記事では、手順に入る前に各ツールの役割を 2〜3 行ずつ並べておく
- **公式手順があるならリンクして差分だけ書く**: 公式のインストール手順やチュートリアルを本文へ書き写さない。リンクを置いた上で、公式どおりに進めると迷う箇所や、自分の用途に合わせて選択を変えた箇所だけを補う。公式が更新されたときに記事が壊れなくなる
- **設定ファイルは全体を見せてから項目ごとに説明する**: 断片だけを並べると、読者はどこに書けばよいか分からない。ファイル全体（または該当ブロック全体）を先に示し、その後で主要なキーの意味を箇条書きにする
- **環境差があるなら併記する**: OS によってコマンドが変わる箇所は、両方をコードブロックで並べる。片方しか書かないと、もう片方の読者はそこで止まる
- **その手順で詰まる点は、その手順の直後に置く**: 記事の末尾にまとめて書くと、読者は詰まった時点では気づけない。バージョンの相性で動かない、特定の設定でないと反映されないといった注意は、該当する手順のすぐ後ろに置く

### 判断と限界の書き方

- **なぜこの構成を選んだかを書く**: 検討して落選した選択肢と、落選した理由を残す。読者は同じ検討を最初からやり直さずに済み、自分の状況では別の選択肢が正しいかどうかも判断できる。実際に試して駄目だった選択肢は、どこで駄目だったかまで書く
- **順序や構成に理由があるなら、その場で書く**: 「A を先に、B を後に実行する」といった順序に理由がある場合、一文で添える。理由のない順序だと思われると、読者は自分の都合で入れ替えて詰まる
- **失敗したときの戻し方を書く**: 既存のファイルを削除する手順、既存の環境を置き換える手順を含む記事では、元に戻す方法を書く。戻し方が分からない手順は、本番環境に近いところでは実行されない
- **できないことを書く**: 導入しても解決しない範囲を明示する。手順型の記事は利点だけを並べがちで、読者は導入すればすべて解決すると理解する。「これはローカルでのチェックなので、リポジトリ側での検証は別に必要」のような一文が、読者の設計判断を変える
- **末尾を総論にしない**: 「誰でも簡単に構築できます」で締めない。末尾に置くのは、実際に運用して分かったつまずきやすい点、または導入後に効いた具体的な変化である

### 見出し構成の型

見出し名はそのまま使わず、記事の題材に合わせて内容のある名詞句へ置き換える。「導入手順」「設定」のような役割名だけの見出しは、対象で切る構成のときに同じ名前が何度も並んで目次が機能しなくなる。

工程で切る場合（対象が 1 つのツールで、インストールから公開まで通す記事）。

```text
## （完成状態を見せる見出し）  ← 画像・GIF・最終的な設定ファイル
## 前提                         ← 必要なランタイム・ツール・バージョン
## （導入と初期化）             ← 上から流せるコマンド列
## （設定ファイルの中身）       ← 全体を見せてから項目ごとに説明
## （動作確認と公開）
## （選定理由・つまずいた点）   ← 落選した選択肢、戻し方、限界
```

対象で切る場合（複数のツールを組み合わせる記事）。

```text
## （完成状態を見せる見出し）
## サンプルリポジトリ           ← 動く一式へのリンク
## 利用ツールについて           ← 各ツールの役割を 2〜3 行ずつ
## 前提
## ツール A                     ← インストール / 設定
## ツール B                     ← インストール / 設定
## （連携させる手順）
## （実際に動かす）             ← 順序に理由があるならここで書く
## （運用上の注意・限界）
```

後者では、各ツールの節を「インストール」「設定」の H3 で揃える。読者は詰まった箇所へ戻るとき、同じ構造を頼りに探す。

## セルフレビュー項目

`review.md` の共通点検に加えて、次を確認する。

- [ ] 使うツールを、名称と定義の紹介からではなく、それが何を解決するかから説明しているか
- [ ] 手順の理解に必要な説明まで、公式ドキュメントへのリンクで済ませていないか
- [ ] 完成状態（スクリーンショット・GIF・最終的な設定ファイル）を冒頭で見せているか
- [ ] 前提環境が独立した節にまとまっているか
- [ ] 手順を上から順に実行して再現できるか。後出しの前提が混ざっていないか
- [ ] インストールするツールのバージョンを明示しているか
- [ ] 各手順が何のために必要かを一文で説明しているか
- [ ] 公式手順を書き写さず、リンク + 差分で済ませているか
- [ ] 設定ファイルを断片ではなく全体で見せ、主要な項目を説明しているか
- [ ] その手順で詰まる注意点が、末尾ではなく該当手順の直後に置かれているか
- [ ] なぜこの構成・この順序を選んだかを書いているか
- [ ] 既存の環境やファイルを壊す手順に、戻し方が添えられているか
- [ ] 導入しても解決しない範囲を書いているか
- [ ] 末尾が「簡単に構築できます」のような総論で終わっていないか
