# 執筆規則

執筆に入るときに読む。規則は強さで 3 段階に分けてある。

- **必須**: 違反したら記事として成立しない。例外はない
- **原則**: 守る。外す場合は、なぜ外すのかを説明できる必要がある
- **推奨**: 目安。題材や記事の長さに応じて変えてよい。努力目標という意味ではなく、外すときは意識して外す

`/stop-ai-slop-jp` が持つ規則（false agency、反証可能性、AI 偏愛語、中間温度、両論併記）は本ファイルに再掲しない。執筆時にそちらを併用する。

## 必須

- **確認できない事実を断定しない**: 自分で確認した事実は言い切る。推測・伝聞・未検証の情報には「らしいです」「ようです」「と思います」を残す。断定した一文が誤りだと、記事全体が一次情報として信用できなくなる
- **実行できないコードを実行可能として載せない**: 擬似コードや省略したコードを、そのまま動くコードとして置かない。省略する場合は省略したと明記する。読者はコードブロックをコピーして実行する
- **主張に必要な因果関係を省略しない**: 「A だと B になる」で止めず、その間で何が起きているかを一文で足す。「pip install だけではコマンドが shims に配置されないから、パスが通らない」まで書けば、読者は似た状況に遭ったとき自力で当たりをつけられる。機構が書かれていない因果は、読者が何も持ち帰れない
- **`private: true` を維持する**: 記事は限定共有の状態で完成させる。公開の判断はユーザーが行う

## 原則

### 立ち位置

- **私の経験から書く**: 「○○について解説します」ではなく、「○○をやったらこうなった」から入る
- **主語は「私」で統一する**: 「我々」「筆者」「本稿では」を使わない
- **読者の時間を尊重する**: 前提知識の説明は最小限にし、公式ドキュメントへのリンクで済ませる。ただし主張の理解に必要な説明はリンクで代替しない

### 説明の組み立て

情報を網羅することより、読者の頭の中に一貫した理解モデルを作ることを優先する。

- **具体から抽象へ進む**: コード・コマンド・エラーメッセージを先に見せて、それから説明する
- **問題起点で説明する**: 従来方式 → 起きる問題 → 必要になる性質 → 新しい技術 → 解決 → 新しく生じる制約、の順で書く。名称や定義から始めない。「pnpm とは」ではなく「yarn v1 の node_modules で何が起きて、何が必要になったか」から入る
- **既知と未知を分離する**: 「変わらない部分」を先に示してから「変わった部分」を示す。「コマンド体系と lockfile の役割は同じ。変わるのは node_modules の構造だけ」と書けば、読者は既存の理解に差分として追加できる
- **専門用語は役割を説明した後に導入する**: 日常語で役割を説明 → 具体的な動きを示す → 専門用語を付ける → 以降は専門用語を使う。「content-addressable store に…」より先に「一度取得したパッケージを一箇所に貯めて、各プロジェクトからはそこを指す」を書く
- **詳細度を階層化する**: 本文（主張の理解に必要）/ 補足（飛ばしても本筋を追える）/ 発展（実装詳細・例外・派生）に分ける。判断基準は「その説明を読まなくても次の節の因果関係を理解できるか」。理解できないなら本文に置く
- **図には一つの役割だけを持たせる**: 一枚で全体を説明しようとしない。データの流れ、従来方式との違い、時系列の変化のどれか一つに絞る。図を置いたら、どこを見るべきかを文章で示す
- **単純化した箇所を明示する**: 省略したことと、省略してよい理由を書く。細部の省略や例外の後回しは許容する。実際とは異なる因果関係を書くことは許容しない（読者が後で理解を修正することになる）
- **トレードオフを示す**: 何が改善され、何が悪化し、どの条件で有効か。利点だけを書くと、読者はその技術を万能だと理解する

### 見出し

- **見出しは名詞句にする**: 「○○は△△だ」という命題型 H2 を使わない。命題型は結論を見出しで言い切ってしまい、本文がその要約にしかならない
- **「はじめに」「まとめ」を使わない**: 冒頭は本題から入り、末尾は最後の節で自然に閉じる

### 文体と段落

- **ですます調で統一する**: ただし「です」「ます」の単調な繰り返しを避け、「でした」「でしょう」「ません」「ですが」「ました」などで変化をつける
- **一文一改行**: 段落の区切りは空行
- **一つの段落には一つのトピックだけを置く**: 段落の最初の文を読めば、何の話かわかるようにする
- **同じ主張を言い換えて繰り返さない**: 一つの主張は一度だけ書く

### コードブロック

- ファイルパスや言語をコードブロックのメタデータに指定する
- 長いコードは分割して、各ブロックの前に何をしているかを一文で説明する

### タイトルとタグ

- タイトルには、読者が検索しそうなキーワードを含める
- タイトルには主張か状況を具体的に書く。「〜について」「〜のまとめ」で終わらせない。悪い例:「Terraform のエラー対処」→ 良い例:「AFT で OU 未登録エラーが出たときの回避策」
- タグは技術名・ツール名を優先する（例: `Terraform`, `AWS`, `ControlTower`）
- 「初心者」「入門」のような属性タグは、記事の主な読者層に合致する場合のみ付ける
- タグは Qiita で既存のタグ名に合わせる（表記揺れを避ける）

### 外部ページへの参照リンク

公式ドキュメントなど外部ページのリンクは、`<>` で囲まず、前後に空行を挟んだ裸の URL（bare URL）で書く。

```text
（前の段落）

https://example.com/docs

（次の段落）
```

Qiita は単独行の裸 URL をカード表示するが、`<>` で囲むとカードにならない。VSCode の markdownlint（MD034）が保存時に `<>` を付けるため、`.vscode/settings.json` の `markdownlint.config` で MD034 を無効化している（`.vscode` 全体は gitignore だが、この設定だけは明示的にコミットして共有）。

## 推奨

- タイトルは 30〜50 字程度。短すぎると内容が伝わらず、長すぎると検索結果で切れる
- タグは最大 5 つ。多すぎると焦点がぼやける
- 記事を駆動する軸は 3〜5 個
- 抽象と具体を短い間隔で往復する。抽象説明 → 具体例 → 例の中で何が起きたか → 抽象的な意味の再確認。抽象を複数段落続けず、例を出しただけで終わらせない
- `/stop-ai-slop-jp` の採点で 35/50 以上を目指す
