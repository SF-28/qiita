# 概念解説型の記事の書き方

## いつ読むか

概念解説型の記事（新しい概念を複数導入し、読者の理解モデルを作る記事）を書くときに読む。ハマりどころ型は `troubleshooting.md`、手順型は `howto.md`、体験記型は `experience.md` を読む。それらの記事に本ファイルのテンプレートを当てると、「入力と出力」「何は解決できないか」といった節が生えて冗長になる。

読むタイミングは記事タイプを概念解説型と判定した直後、構成を決める前。

## 必要な入力

共通の核（`planning.md`）に加えて、次を確定する。

| 項目 | 問い | 悪い例 | 良い例 |
| --- | --- | --- | --- |
| 読者の現在地 | 読者がすでに理解していることは何か？ | 「なんとなく知っている」 | 「Terraform の apply は日常的に使うが、Control Tower は触ったことがない」 |
| 理解の断絶 | 読者はどこで理解できなくなるか？ | （未定義） | 「AFT の apply が通ることは分かる。しかし OU の登録がいつ必要になるかが分からない」 |
| 導入する概念と依存関係 | どの概念を、どの順で理解させるか？ | 「関連する用語を一通り紹介する」 | 「アカウントリクエスト → OU 登録 → アカウントカスタマイズの順。前を理解しないと次が読めない」 |

「理解の断絶」は「A は分かる。しかし A から B へどうつながるかが分からない」の形で一文にする。この一文が、記事が解消する疑問そのものになる。

依存関係が書き出せない概念は、記事に入れる理由がない可能性が高い。この時点でスコープ外へ出すことを検討する。

## 記事の骨格

| 位置 | 置くもの |
| --- | --- |
| 冒頭 | 読者の現在地 → 断絶 → この記事で分かること |
| 駆動軸 | 概念の依存関係（3〜5 個） |
| 末尾 | 因果のつなぎ直し |

この型で冒頭に置くのは**読者の現在地**である。読者は概念を知りたいのではなく、いま理解できていない一点を埋めたくて読む。記事は「読者がすでに分かっていること」から始め、そこから断絶へ橋を架ける。

駆動軸は時系列でも手順でもなく、概念どうしの依存関係である。A を理解しないと B が理解できない、という順序がそのまま記事の並び順になる。調査した順に並べると、読者は依存関係を自分で組み直すことになる。

## 固有の書き方

### 記事全体の流れ

概念解説型の記事は、次の順序で組み立てる。

```text
読者の現在地
↓
理解できていない断絶
↓
全体像（説明の軸 3〜5 個）
↓
既存技術の限界
↓
新しい概念
↓
新しい概念が問題を解決する仕組み
↓
全体システムへの統合
↓
できることと限界
↓
理解の再整理（因果のつなぎ直し）
```

各節の冒頭で、全体像のどこを説明しているかを示す。「ここからは、4 つの軸のうち『評価の粒度』を見ていく」の一文があるだけで、読者は現在位置を見失わない。

### 概念説明ブロックの 6 要素

記事の主張を理解するために不可欠な概念には、独立した説明ブロックを設ける。順序も 6 要素で固定する。

| 要素 | 書くこと | 注意 |
| --- | --- | --- |
| 一文定義 | その概念の役割を一文で表す | 定義に専門用語を入れない。日常語だけで書く |
| 解決する問題 | それがなければ何に困るか | 「便利になる」ではなく、困る場面を具体的に書く |
| 入力と出力 | 何を受け取り、何を返すか | ここを書くと概念がブラックボックスになりにくい |
| 処理の流れ | 内部処理を 3〜5 段階に分ける | 数式や実装を省略しても、処理そのものは省略しない |
| 最小具体例 | 短い例で実際の動きを確認する | 例を示すだけで終わらせず、例の中で何が起きたかまで書く |
| できること / できないこと | 能力と限界の両方 | 限界の記述が、次の概念を導入する理由になる |

段階を 2 つに圧縮したり、「詳細は公式ドキュメント参照」で処理の流れを飛ばしたりすると、読者は用語を覚えただけの状態で読み終わる。

### 概念間の依存関係

複数の新概念が登場する場合、それぞれを独立して説明するだけでは足りない。概念を説明し終えるたびに、次の 3 つの問いへ答える。

- この概念は、直前の概念とどう関係するか
- この概念が加わることで、システム全体はどう変わるか
- この概念がなければ、何ができないか

### 標準テンプレート

見出し名はそのまま使わず、記事の題材に合わせて内容のある名詞句へ置き換える。特に最後の節は「## まとめ」にしない。「なぜこの構成に落ち着いたのか」のように、その記事で再構築する因果が分かる見出しにする。

```text
## この記事で解決する疑問

- 読者が現在理解していること
- 理解できていない断絶
- 記事を読むと何が分かるか

## 前提知識

- 必要な前提
- 記事内で説明する概念
- 扱わない範囲

## 先に全体像

- 結論
- 主要な構成要素
- 説明の軸

## 従来方式

- どのような仕組みか
- 何ができるか
- どこに限界があるか

## 新しい方式が必要になった理由

- 解決したい問題
- 必要になる性質
- 従来方式では難しい理由

## 新概念 A

- 一文定義
- 解決する問題
- 入力と出力
- 処理の流れ
- 最小具体例
- できること / できないこと

## 新概念 B

- 一文定義
- 解決する問題
- 入力と出力
- 処理の流れ
- 最小具体例
- 新概念 A との関係
- できること / できないこと

## 全体としてどう動くか

- 各概念をどの順序で使うか
- データがどう流れるか
- 最終的に何が出力されるか

## 利点とトレードオフ

- 改善されること
- 新しく発生する問題
- 適している条件 / 適していない条件

## 実際にはもう少し複雑な点

- 単純化した箇所
- 例外
- 詳細を学ぶためのキーワード

## （因果を再構築する見出し）

- 従来方式の問題
- 導入された概念
- 問題が解決される仕組み
- 残る限界
```

### 新概念の説明テンプレート

```text
### 概念名

一文でいうと、〇〇するための仕組みです。

#### なぜ必要か

従来の〇〇では、△△という問題があります。

この問題を解決するには、□□できる必要があります。

#### 何を入力して、何を出力するか

入力

- 〇〇
- △△

出力

- □□

#### どのように動くか

1. 〇〇する
2. △△を比較する
3. □□を選ぶ
4. 結果をまとめる

#### 具体例

〇〇という状況を考えます。

この場合、内部では△△が起きます。

その結果、□□になります。

#### 何ができるようになるか

- 〇〇
- △△

#### 何は解決できないか

- □□
- ××

#### 他の概念との関係

この概念は〇〇を扱います。

一方、△△は□□を扱います。

両方を組み合わせることで、××を実現します。
```

### この型の中心原則

技術記事の品質は、次の三つに分けて考える。

- **読みやすさ**: 文章を負担なく読み進められること
- **分かりやすさ**: 説明されている内容を、その場で理解できること
- **理解の持続性**: 読後に概念同士の関係を再現できること

文章や図を単純にすれば読みやすさは上がる。しかし重要な新概念の仕組みまで省略すると、分かりやすさと理解の持続性は下がる。

目指すのは情報を削ることではなく、本筋を妨げない順序で、必要な情報を段階的に提示することである。

## セルフレビュー項目

`review.md` の共通点検に加えて、次を確認する。

### 記事全体

- [ ] 新しい技術・概念を、名称からではなく解決する問題から説明しているか
- [ ] 記事を駆動する軸が絞られ（3〜5 個）、各節がどの軸の話か分かるか
- [ ] 主張の理解に必要な説明を、補足や「詳細は公式ドキュメント参照」へ追いやっていないか
- [ ] 末尾が用語や設定の再掲だけで終わっていないか。因果のつなぎ直しになっているか

### 個々の新概念

- [ ] 一文で役割を説明できているか
- [ ] なぜ必要なのかを説明しているか
- [ ] 入力と出力が分かるか
- [ ] 処理の流れを追えるか
- [ ] 最小具体例があるか
- [ ] 他の概念との関係が分かるか
- [ ] できないことも説明しているか

### 読後の理解

読み終えた読者が、記事を見返さずに次を説明できるかで判定する。

- [ ] その技術がなぜ存在するのかを説明できるか
- [ ] その技術がどの問題を解決するのかを説明できるか
- [ ] 各概念の依存関係を説明できるか
- [ ] 用語を忘れても、仕組みを説明できるか
