# 核の確定と構成設計

記事の核をユーザーと固めるとき、および H2 構成を設計するときに読む。ここに書くのは全タイプ共通の部分だけである。タイプごとに確定すべき入力と、冒頭・末尾に置くものは、判定したタイプの参照ファイルにある。

## 対話の原則

核の 5 項目は、ユーザーが最初から答えられるものではない。テーマを話しながら形になっていく。聞き出すのではなく、一緒に作る。

項目を並べて一括で埋めさせると、「エンジニア全般」「Terraform について」のような空欄埋めが返ってくる。それは下の表で悪い例として挙げているものそのものである。

- **一度に聞くのは 1〜2 問**
- **先に仮案を出す**。ゼロから答えさせず、こちらの案を直してもらう形にする
- **すでに分かることは聞かない**。素材・会話履歴・リポジトリから読み取れるものは埋めて、確認だけ取る
- **項目名で聞かない**。「スコープは？」ではなく「○○も書きますか、それとも別記事にしますか」
- **収束させる**。3 往復しても絞れないなら、一番強い案を選んで「これで進めます」と宣言する。最適解を証明しようとしない

## 進め方

### 1. 素材を読み取り、仮案を提示する

テーマと素材から読み取れたことをまとめて提示する。ユーザーは違うところだけ直せばよい。

```text
テーマから、こう読み取りました。違うところを教えてください。

- 記事タイプ: ハマりどころ型（症状 → 原因 → 回避策で書く）
- 主張の候補
  A. AFT の OU 未登録エラーは、実際には OU ではなく渡した値の形式が原因
  B. AFT を使うなら、apply の前に OU を作っておく必要がある
- 読者: AFT で Organization を管理しようとして apply が落ちた人
```

素材が乏しくて仮案が作れないときだけ、テーマを掘り下げる質問をする。

### 2. 弱い項目から 1 つずつ埋める

優先順は 主張 → 読者 → 根拠 → スコープ → 差分。主張が決まらないと他が決まらない。差分は他が埋まれば自然に見えるので最後でよい。

| 項目 | 項目名を出さない聞き方 |
| --- | --- |
| 主張 | 「読んだ人に一番持ち帰ってほしいことは何ですか」 |
| 読者 | 「どういう状況の人が読むと、一番役に立ちますか」 |
| 根拠 | 「これは実際にやったことですか、調べた内容ですか」 |
| スコープ | 「○○も書きますか、それとも別記事にしますか」 |
| 差分 | こちらで既存記事を調べ、「既存記事との違いはここだと思います」と提示する |

タイプ固有の入力（読者の理解の断絶、症状と再現環境、到達状態、着手時点の自分など）も、この段階で同じ要領で埋める。列挙は判定したタイプの参照ファイルの「必要な入力」にある。

### 3. 核をまとめて確認する

埋まったら、一度だけまとめて提示する。ここで初めて項目名を並べる。埋まっていない項目があれば、埋まっていないと明示する。空欄のまま書き始めない。

### 4. 打ち切りの判断

| 状況 | 動き |
| --- | --- |
| 「任せる」「一気に書いて」「構成も任せる」 | 仮案を確定として構成へ進む |
| 素材が十分にある（作業ログ・検証結果が揃っている） | 確認を最小にして進む |
| 主張が 3 往復で絞れない | 一番強い案を選んで宣言し、進む |
| 根拠が「調べた内容」しかない | スコープを根拠のある範囲まで縮めるか、テーマ自体を変える提案をする |

## 核の判定基準

対話で埋めた内容が十分かを、こちらで判定するための基準。この表をそのままユーザーに見せて埋めさせない。

| 項目 | 何が確定していればよいか | 悪い例 | 良い例 |
| --- | --- | --- | --- |
| 主張 | この記事で言い切ること | 「Terraform は便利」 | 「Control Tower の OU 未登録エラーは AFT のドキュメントに書いていない。こう回避する」 |
| 読者 | 誰が、どういう状況で読むか | 「エンジニア全般」 | 「AWS Organization を初めて AFT で管理しようとして詰まった人」 |
| 差分 | 既存記事と何が違うか | 「まとめ記事」 | 「公式ドキュメントにない回避策と、なぜそうなるかの内部挙動の説明」 |
| スコープ | 何を書かないか | （未定義） | 「Control Tower 自体の導入手順は扱わない」 |
| 根拠 | 何をもとに書くのか | 「調べた内容」 | 「自分で AFT を構築して踏んだエラーと、その切り分けログ。公式ドキュメントの該当ページ」 |

「根拠」は、実際にやった作業・自分で取った検証結果・一次情報のどれかを指す。これが空のまま書き始めると、他人の記事の要約を並べただけの伝聞記事になる。手を動かしていない領域は、根拠のある範囲までスコープを縮める。

核が曖昧なまま書くと、AI っぽい総論記事になる。ユーザーが「とりあえず書いて」と言っても、最低限「主張」と「読者」は仮案を提示して合意を取る。

## 構成設計

核をもとに、見出し構成（H2 レベル）を箇条書きで組み立てる。

守ること:

- 見出し名は `writing.md` の原則に従う
- 読者の問いの順に並べる。書き手の調査順ではなく、読み手が知りたい順
- 記事を駆動する軸を絞る。各 H2 がどの軸・どの段階の話かを自分で言えない構成は、軸が多すぎるか曖昧
- 冒頭の節と末尾の節は、判定したタイプの参照ファイルの「記事の骨格」に沿って置く。入口と締めはタイプごとに別物である

禁止しているのは中身のない見出し名と、儀式的な前置き（記事の自己紹介、これから書くことの予告）であって、冒頭と末尾の役割ではない。タイプごとの入口を示すことは前置きではなく本題の入口にあたる。入口と締めは、内容のある見出しで置く。

```markdown
## apply が `OU is not registered` で失敗する   ← 冒頭（症状と再現環境）
## 回避策: apply の前に OU を作る                ← 本論
## なぜこの順序が必要だったのか                   ← 末尾（再発を防ぐ条件）
```

上はハマりどころ型の例で、冒頭が症状、末尾が再発を防ぐ条件になっている。いずれも名詞句か疑問形で、内容が見出しから分かる。入口と締めに何を置くかはタイプごとに変わるため、判定したタイプの「記事の骨格」を見て決める。
