# ハマりどころ型の記事の書き方

## いつ読むか

ハマりどころ型の記事（特定の失敗に遭遇し、その原因と回避策を残す記事）を書くときに読む。概念解説型は `concept.md`、手順型は `howto.md`、体験記型は `experience.md` を読む。

読むタイミングは記事タイプをハマりどころ型と判定した直後、構成を決める前。この型の読者は記事を読みに来るのではなく、**エラーメッセージを検索して流れ着く**。冒頭から順に読む読者を想定した構成にすると、必要な情報にたどり着けない。

## 必要な入力

共通の核（`planning.md`）に加えて、次を確定する。

- **症状**: エラーメッセージの原文、または観測した現象。要約ではなく実際に出力された文字列
- **再現環境とバージョン**: OS・ランタイム・ライブラリ・プラットフォームのバージョン
- **原因と、そう判断した根拠**: 何が起きていたか。なぜそう言えるか（ログ、設定値、公式ドキュメントの記述、切り分けの結果）
- **回避策**: 実際に症状が消えた手順。その場しのぎか恒久対策かの区別も含む
- **検証した結果**: 回避策を適用したあとに何が起きたか。未検証の対策があるならどれか
- **再発条件**: 次に同じ構成を組むときに、どこを見れば同じ症状を避けられるか

原因が特定できていない場合は、特定できていないことを前提に書く。推測を原因として断定しない。

## 記事の骨格

| 位置 | 置くもの |
| --- | --- |
| 冒頭 | 遭遇した症状（エラー・現象）と再現環境 |
| 駆動軸 | 症状 → 原因 → 回避策 |
| 末尾 | 再発を防ぐ条件 |

この 3 段階は 1 記事に 1 セットとは限らない。1 つの構成で複数の症状に当たった場合は、症状ごとに H2 を立てて 3 段階を繰り返す。逆に 1 つの症状を深く追った記事では、H2 を「症状」「環境」「原因」「回避策」に割り当てる。

末尾を「まとめ」にしない。読者は原因と回避策をすでに読んでいるので、同じ内容を再掲しても得るものがない。末尾に置くのは、次に同じ構成を組むときに見落とさないための条件である。見落としがちな設定のチェックリスト、あるいは同じ症状に再会したときの切り分け手順を番号付きで置く。

## 固有の書き方

### 症状の書き方

- **エラーメッセージは原文のまま貼る**: 要約したり日本語に言い換えたりしない。読者はそのメッセージを検索窓に貼って来る。原文がなければ記事に到達できない。「取得に失敗する」とだけ書いた記事は、同じ症状の読者に見つからない
- **症状を見出しにする**: 見出しは「原因」「解決策」のような役割名ではなく、「コンテナイメージの取得に失敗する」「ヘルスチェックが失敗してタスクの停止と起動が繰り返される」のように、読者が観測する現象そのものにする。複数の症状を扱う記事では、これが目次から自分の症状を探す唯一の手がかりになる
- **環境とバージョンを冒頭にまとめる**: OS・ランタイム・ライブラリ・プラットフォームのバージョンを箇条書きで並べる。同じエラーメッセージでも、バージョンが違えば原因も回避策も変わる。特に、原因がその環境固有である場合（Windows 版の実装、特定のプラットフォームバージョン）は、環境の記述そのものが原因の一部になる
- **症状は一度だけ提示する**: 「はじめに」でエラーを貼り、「発生したエラー」で貼り直し、「まとめ」でもう一度貼る、という重複を作らない。同じコードブロックが 3 回出てくると、読者は差分を探して読み直すことになる

### 原因の書き方

- **切り分け過程を残すかは、エラーメッセージが原因を正しく指しているかで決める**: メッセージが原因を直接指しているなら（「curl が見つからない」→ curl を入れる）、切り分けは書かずエラーと対処だけを並べる。指していないなら（「OU が登録されていない」と出るが実際は渡した値の形式が不正）、切り分け過程を残す。後者では、読者もメッセージを額面通りに受け取って同じ回り道をするからである
- **外れた仮説は「外れた」と明記する**: 最初に疑った候補を列挙し、それを確認しても解消しなかったと書く。うまくいった経路だけを残すと、読者は同じ候補を最初から潰し直すことになる。外れた仮説の記録は、読者の時間をそのまま節約する
- **登場コンポーネントが多いときは、先に関係を示す**: 複数のサービスやレイヤを経由して症状が出る場合、どの層が何を担当しているかを図か箇条書きで示してから原因に入る。どの層に渡す値なのかが分からないままでは、原因の説明が理解できない
- **名前から推測される挙動と実際の挙動がずれているなら、そのずれ自体を書く**: 設定名やパラメータ名から自然に読み取れる意味と、実際の動作が違うことが原因になっている場合がある。ずれを指摘することが、読者にとって記事の一番の価値になることがある

### 回避策の書き方

- **修正前と修正後を並べる**: 差分だけを書かず、動かなかったコードと動くコードの両方を載せる。読者は自分の手元のコードと修正前を突き合わせて、同じ症状かどうかを判断する
- **回避策と恒久対策を区別する**: その場をしのぐ手順（毎回コマンドを打つ、値を手で書き換える）と、根本的に不要にする手段（自動化するプラグイン、設定側の修正）は分けて書く。同じ節に混ぜると、読者はどちらを選ぶべきか判断できない。恒久対策が未検証なら、未検証であることを添える
- **公式ドキュメントとの関係を明示する**: 記載があるなら該当ページへリンクし、どこに書かれているかを一文で示す。記載がないなら、探した上で見つからなかったという事実を書く。記載はあるが読み違えやすい書き方なら、どう読み違えたかを書く。この一文があるかどうかで、記事が一次情報として持つ価値が変わる
- **症状が連鎖する場合は対応表にする**: 1 つ直すと次のエラーが出る、という順に詰まった場合、経緯を散文で書かずエラーと対処の対応で並べる。読者は自分が今どのエラーで止まっているかを一目で探せる。可能なら、全部を反映した最終形（Dockerfile や設定ファイル全体）を先に置く

### 見出し構成の型

見出し名はそのまま使わず、記事の題材に合わせて内容のある名詞句へ置き換える。特に「症状」「原因」「解決策」という役割名は、複数の症状を扱う記事では機能しない。

症状が 1 つで、原因の特定に手間取った場合は、切り分けの過程を軸にする。

```text
## 遭遇したエラー          ← エラー原文をそのまま貼る
## 環境                    ← バージョン・構成
## やりたかったこと        ← 何をしようとして踏んだのか
## 最初に疑ったこと        ← 外れた仮説と、それを潰した結果
## （登場する要素の関係）  ← 層が多いときだけ。原因を理解する土台
## 原因                    ← 機構まで書く
## 修正前 / 修正後         ← 動かないコードと動くコードを並べる
## （再発を防ぐ条件）      ← 次に同じ症状を見たときの切り分け手順
```

症状が複数ある、または 1 つ直すと次が出る形で連鎖した場合は、症状ごとに節を立てる。

```text
## ざっくり構成            ← 何を組もうとしていたか
## 環境                    ← バージョン・構成
## （最終的な解決形）      ← 全部反映した設定ファイルやコマンド一式
## （症状 1 を現象で書いた見出し）
    原因 → 回避策
## （症状 2 を現象で書いた見出し）
    原因 → 回避策
## （見落としがちな設定）  ← 同じ構成を組むときのチェックリスト
```

後者では、症状ごとの節を短く保つ。原因が一文で書けるなら一文で終える。この型の記事は最後まで読まれることを前提にしない。

## セルフレビュー項目

`review.md` の共通点検に加えて、次を確認する。

- [ ] 登場する技術や設定を、名称と定義の紹介からではなく、それが症状にどう関わるかから書いているか
- [ ] 原因の理解に必要な説明を、補足や「詳細は公式ドキュメント参照」へ追いやっていないか
- [ ] エラーメッセージや現象を原文のまま載せているか（要約や言い換えで置き換えていないか）
- [ ] 見出しが役割名ではなく、読者が観測する症状になっているか
- [ ] 環境・バージョンが冒頭にまとまっているか
- [ ] 切り分け過程を残す / 省くの判断が、エラーメッセージが原因を指しているかに基づいているか
- [ ] 外れた仮説が「外れた」と分かる形で残っているか
- [ ] 修正前と修正後の両方が載っているか
- [ ] 回避策と恒久対策が区別されているか
- [ ] 公式ドキュメントに記載があるか・ないか・読み違えやすいかを書いているか
- [ ] 末尾が再掲ではなく、再発を防ぐ条件（チェックリストや切り分け手順）になっているか
